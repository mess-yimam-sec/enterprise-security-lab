# Milestone 5 — VPC Flow Logs & Network Traffic Investigation

## Overview

In this milestone, I moved beyond simply enabling VPC Flow Logs and focused on validating that the logging pipeline could capture real network activity inside my private AWS environment.

The goal was to connect several parts of the lab into one practical security workflow:

**Private network traffic → VPC Flow Logs → CloudWatch Logs → investigation**

This exercise also reinforced how Terraform, IAM, GitHub Actions, CloudTrail, and AWS networking work together during deployment and troubleshooting.

## Starting Point

The lab already had a private subnet (`10.10.2.0/24`) with no NAT Gateway and no direct internet route. VPC Flow Logs were enabled for the private subnet and configured to send network-flow metadata to the CloudWatch log group:

`/enterprise-security-lab/vpc-flow-logs`

The log group uses a short retention period to keep the lab cost-conscious.

At first, the Flow Log streams were created successfully, but the records showed `NODATA`. This was an important reminder that having the logging infrastructure in place does not automatically create meaningful network telemetry. There must be actual traffic for Flow Logs to observe.

## Creating Real Network Traffic

To test the logging path more reliably, I deployed two temporary Amazon Linux EC2 instances in the private subnet using Terraform.

Neither instance received a public IP. One instance acted as the **traffic generator**, while the second acted as the **target**:

- Traffic generator: `10.10.2.84`
- Target: `10.10.2.40`
- Test protocol: TCP
- Destination port: `443`

Terraform dynamically referenced the target instance's private IP in the generator configuration. When the generator started, it made repeated TCP connection attempts to the target on port 443.

This gave me deterministic traffic between two real network interfaces inside the private subnet.

## Validating the Flow Log

After the test instances generated traffic, CloudWatch contained a real VPC Flow Log record:

```text
2 149957954264 eni-0a562ed36c8efc00e 10.10.2.84 10.10.2.40 46428 443 6 1 60 1791242586 1791242616 ACCEPT OK
```

The important fields showed:

| Field | Value | Interpretation |
| --- | --- | --- |
| Source IP | `10.10.2.84` | Traffic-generator EC2 |
| Destination IP | `10.10.2.40` | Target EC2 |
| Source port | `46428` | Temporary client-side port |
| Destination port | `443` | Port being tested |
| Protocol | `6` | TCP |
| Packets | `1` | Packet represented in the flow |
| Bytes | `60` | Bytes represented in the flow |
| Action | `ACCEPT` | Traffic was permitted by the applicable VPC network controls |
| Log status | `OK` | Flow Log data was recorded normally |

A key lesson was that `ACCEPT` does not necessarily mean that an application successfully accepted the connection on port 443. It indicates that the traffic was permitted by the applicable network controls at the capture point.

VPC Flow Logs provide network-flow metadata rather than packet payload contents.

## How the Pieces Fit Together

```text
Terraform / GitHub Actions
          |
          v
        AWS VPC
          |
     Private Subnet
      10.10.2.0/24
          |
    +-----+------+
    |            |
Generator      Target
10.10.2.84 --> 10.10.2.40:443
    |
    v
VPC Flow Logs
    |
    v
CloudWatch Logs
    |
    v
Network Investigation
```

The actual TCP traffic is the event occurring on the network. VPC Flow Logs observe that traffic and create metadata describing the flow. CloudWatch Logs provides the centralized location where those Flow Log records can be retained, searched, and investigated.

This helped me connect AWS-native logging with concepts I have worked with in SIEM environments: security events are generated by systems and network activity, collected centrally, and then used for investigation and detection.

## Troubleshooting and CloudTrail

This milestone also included an unexpected but useful troubleshooting exercise.

During an earlier test, an EC2 instance was terminated and replaced. Rather than assuming what happened, I reviewed AWS activity and Terraform deployment information.

CloudTrail showed that the `TerminateInstances` API operation had been called through the GitHub Actions Terraform deployment role. Reviewing the Terraform Apply output then confirmed that Terraform had intentionally replaced the instance as part of the infrastructure change.

This demonstrated another useful investigation path:

```text
Unexpected infrastructure change
          |
          v
CloudTrail API activity
          |
          v
IAM / assumed role identity
          |
          v
GitHub Actions deployment
          |
          v
Terraform Apply output
          |
          v
Root cause confirmed
```

## IAM and Terraform Lessons

Terraform needs more than resource-creation permissions.

During planning and deployment, Terraform refreshes resource state and evaluates data sources. This required several EC2 read operations and access to the AWS Systems Manager public parameter used to retrieve the Amazon Linux 2023 AMI.

I kept the GitHub Actions **Plan role read-oriented** rather than granting it EC2 deployment permissions. The separate **Terraform Deploy role** is used for infrastructure changes through the protected deployment workflow.

This reinforced an important design principle in the lab:

**Validation and deployment should not automatically have the same permissions.**

## What I Learned

This milestone was not just about turning on a logging feature. The most useful part was following the complete path from infrastructure configuration to real traffic and finally to security telemetry.

I was able to:

- Configure private-subnet VPC Flow Logs and CloudWatch delivery.
- Recognize why an active logging pipeline could still report `NODATA`.
- Generate controlled TCP traffic between two private EC2 instances.
- Identify source and destination IP addresses, ports, protocol, packet/byte information, and Flow Log action.
- Distinguish network-level `ACCEPT` from application-level connection success.
- Use CloudTrail and Terraform output together to investigate an infrastructure change.
- Continue separating Terraform planning permissions from deployment permissions.
- Relate AWS network telemetry to familiar SIEM collection and investigation concepts.

## Next Step

The temporary EC2 instances were created specifically for Flow Log validation and should be removed through Terraform after testing so that Terraform state remains consistent and unnecessary EC2/EBS costs are avoided.

The next phase of the lab will build on this work by exploring secure administrative access to private EC2 instances and interactive host-to-host network testing while preserving the private design — no public IP and no direct inbound SSH from the internet.

That will make it possible to generate traffic interactively and compare how allowed and blocked connections appear in VPC Flow Logs.
